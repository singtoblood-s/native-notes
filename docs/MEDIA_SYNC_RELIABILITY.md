# ไฟล์ใหญ่และ sync บนมือถือ

การแก้ใน source วันที่ 11 กันยายน 2026; ต้อง build และเผยแพร่เว็บเวอร์ชันนี้ก่อนจึงมีผลกับเว็บที่ใช้งานจริง ไม่ต้องเปลี่ยน API หรือ migration ของ backend สำหรับการแก้ครั้งนี้

## การนำเข้ารูปและ PDF

- รูปต้นฉบับรับได้ถึง 50 MiB จากเดิม 12 MiB และ PDF ถึง 250 MiB จากเดิม 50 MiB ขีดจำกัดนี้เป็นการควบคุมทรัพยากรบนมือถือ ไม่ใช่การรับประกันว่าไฟล์ทุกชนิดจะถอดรหัสได้
- รูปคง PNG เมื่อไฟล์เล็กพอ; เมื่อใหญ่เกินจะใช้ WebP และลดความละเอียดตามจำเป็น เป้าหมายทั่วไปไม่เกิน 512 KiB ต่อภาพ และปรับงบต่อหน้าตามจำนวนหน้า PDF ขนาดกระดาษและลายเส้นยังแยกจากภาพพื้นหลัง
- PDF อ่านช่วงข้อมูลจากไฟล์ด้วย PDF.js และปล่อย canvas หลังประมวลผลแต่ละหน้า ไม่อ่านต้นฉบับทั้งไฟล์เข้า main thread ก่อนเริ่มทำงาน PDF.js ยังอาจต้องอ่านข้อมูลมากตามโครงสร้างไฟล์
- ยังคงไม่เกิน 100 หน้าต่อการนำเข้าและงบข้อมูลหลังแปลงประมาณ 38 MiB บันทึกทั้งชุดใน transaction เดียว ยกเลิกหรือไฟล์เสียก่อนบันทึกจะไม่ทิ้งหน้าบางส่วน
- นี่เป็นการลดขนาดภาพที่เก็บในโน้ต ไม่ใช่การแก้ไข/เก็บ PDF ต้นฉบับแบบเวกเตอร์ ไฟล์ต้นฉบับไม่ถูกแก้ไข

## การ sync

- คิวใช้ลำดับการเพิ่มลง SQLite แทนเวลาเครื่อง เพื่อรักษาลำดับสมุด → หน้า และลบ → คืนค่า เมื่อเวลาบนเครื่องย้อนหลัง
- การบันทึกระหว่างเขียนต่อเนื่องไม่เลื่อน sync ที่นัดไว้แล้วให้ช้าออกไปไม่สิ้นสุด และแต่ละรอบส่งสูงสุด 10 ชุดก่อนเปิดโอกาสให้ดึงข้อมูลจากอีกเครื่อง
- รองรับ `resume` และ `pageshow` เพิ่มจาก `online` และ `visibilitychange`; ยกเลิก request เมื่อ freeze/pagehide และลองใหม่ด้วย operation ID เดิม
- deadline ครอบคลุมการรับ response body ด้วย ใช้ 60–300 วินาทีสำหรับส่งตามขนาดข้อมูล และ 300 วินาทีสำหรับดึงข้อมูล ป้องกัน request ค้างถาวรและลด timeout บนเน็ตช้า
- ถ้าเซิร์ฟเวอร์/พร็อกซีตอบ 413 ให้แบ่งชุดเล็กลงตามลำดับเดิม โดยไม่เปลี่ยน operation ID หรือ payload ที่ส่งแล้ว รายการเดี่ยวที่เกินขีดจำกัดจริงยังต้องแก้ขนาดข้อมูล
- การปฏิเสธแบบถาวรเก็บสำเนาในเครื่องก่อนนำรายการออกจากคิว ประมวลผล ACK อื่นและดึงข้อมูลต่อ ไม่ส่งสำเนาที่ถูกปฏิเสธวนซ้ำ สำเนาเหล่านี้ต้องตรวจใน Recovered copies / Documents และใช้ Keep เมื่อต้องการนำหน้ากลับมาใช้งาน; สำเนาที่ยังไม่ Keep เป็นข้อมูลในเครื่องและรวมใน Export archive
- ผล conflict จากเซิร์ฟเวอร์สามารถคืน revision ที่ต่ำกว่าในเครื่องได้ เช่น หลัง restore backup โดยเก็บสำเนางานในเครื่องไว้ และไม่ทับงานใหม่ที่ยังค้างในคิว

## กรณีขอบที่ตรวจ

| กรณี | พฤติกรรม/หลักฐาน |
| --- | --- |
| รูปเกิน 12 MiB, PDF เกิน 50 MiB | Chromium นำเข้า PDF 55 MiB และรูปผ่านตัวเลือกไฟล์; รูป noise จริง 18,578,981 bytes ลดเหลือ 488,960 bytes |
| บีบอัดคุณภาพแล้วยังใหญ่ / ไม่รองรับ WebP | ลดความละเอียดต่อจนเข้า budget; ทดสอบ fallback ด้วย canvas mock ที่คืน PNG |
| ไฟล์เสีย, PDF เกิน 100 หน้า, ยกเลิก | ปฏิเสธอย่างชัดเจนและ cleanup; ไม่บันทึกบางส่วน |
| เขียนต่อเนื่องและคิวเกิน 100 รายการ | sync ระหว่างเขียนและดึงข้อมูลก่อนคิวส่งหมด |
| เน็ตหลุด / body ค้าง / แอป freeze | เก็บรายการ sending เดิมไว้สำหรับ retry; ทดสอบ deadline หลัง headers |
| เวลาเครื่องย้อนหลัง | ทดสอบลำดับ create/delete/restore ด้วย SQLite จริง |
| ACK หาย / ส่งซ้ำ / แก้ระหว่างส่ง | เก็บ operation ID และ payload เดิม; ACK rebases งาน pending เท่านั้น |
| เซิร์ฟเวอร์ปฏิเสธ / สมุดถูกลบบนอีกเครื่อง | เก็บ local recovery และ sync งานอื่นต่อ; ทดสอบเปิด migration ซ้ำแล้วไม่ requeue สำเนา |
| บันทึก recovery ล้มเหลว | SQLite rollback และเก็บรายการต้นฉบับในคิว |
| เซิร์ฟเวอร์ restore revision เก่า | ใช้ authoritative snapshot และยังมีสำเนางาน offline |
| pull ไม่ขยับ cursor | หยุดพร้อมข้อผิดพลาด แทนการยิงคำขอเดิม 1,000 ครั้ง |
| session หมดอายุ / บัญชีต่างกัน | ชุดทดสอบเดิมตรวจ 401, login และ workspace isolation; request ที่กำลังทำงานแยกตาม store |

## รันตรวจซ้ำ

```powershell
cd webApp
npm test
npm run build
$env:QA_LARGE_MEDIA = '1'
npm run test:browser
cd ../cloudflare
npm test
npm run typecheck
```

ทดสอบ SQLite ใช้ `node:sqlite` ที่มีใน Node 22 รุ่นใหม่/Node 24 ไม่เพิ่ม dependency

ยังต้องตรวจบน Android เครื่องจริง: เปิดสองเครื่องในบัญชีเดียวกัน เขียนขณะตัด Wi-Fi สลับแอป/ล็อกจอ แล้วเปิดใหม่ ตรวจทั้งภาพ ลายเส้น ข้อความ และ Recovered copies การทดสอบ Chromium แบบ touch ไม่ยืนยันการจัดการ RAM/แบตเตอรี่ของ Samsung หรือมือถือทุกรุ่น

เว็บไม่สามารถรับประกันการ sync ขณะ OS พักหรือปิด process ได้ จึงเน้นเก็บคิวในเครื่องและกลับมาทำต่อเมื่อเปิดแอป ตาม [Chrome Page Lifecycle](https://developer.chrome.com/docs/web-platform/page-lifecycle-api) การล้างข้อมูลเว็บไซต์ยังลบข้อมูล offline ได้ และ PDF ที่ซับซ้อนมากยังอาจเกิน RAM ของอุปกรณ์
