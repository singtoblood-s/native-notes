# หยุดสมุด conflict ที่เพิ่มเอง

สาเหตุคือทั้งผล push ที่ชนกันและ pull ที่มาถึงระหว่างมีงานค้าง เรียกฟังก์ชันสร้างสมุด/หน้าสำเนาพร้อม ID ใหม่ และนำสำเนากลับเข้าคิว sync อีกครั้ง โดยเฉพาะสมุดที่เป็นเพียงชื่อและ metadata จะเกิดสมุดว่าง `· conflict` จำนวนมาก

## พฤติกรรมใหม่

- ไม่มีเส้นทาง sync ที่สร้างสมุดหรือหน้าสำเนาอัตโนมัติ ทั้ง conflict และ rejection เก็บ snapshot ลงประวัติภายในเครื่องเท่านั้น การ retry operation เดิมไม่เพิ่มประวัติซ้ำ
- ถ้าแก้ข้อมูลเดียวกันจากสองเครื่องพร้อมกัน ใช้ snapshot ที่เซิร์ฟเวอร์รับแล้วสำหรับ operation เก่าที่ชนกัน และเก็บอีกเวอร์ชันไว้ใน Saved versions งานใหม่ที่ยัง pending ไม่ถูกทับและจะส่งต่อด้วย revision ที่อัปเดตแล้ว
- การชนกันของ revision ยังเกิดได้ในระบบหลายอุปกรณ์ แต่จัดการภายใน ไม่แสดงเป็นสมุดใหม่หรือ error เพียงเพราะ revision ชนกัน ข้อผิดพลาดจริง เช่น session หมดอายุหรือ payload ไม่ถูกต้อง ยังต้องแสดงตามสาเหตุ
- Settings → Saved versions แสดงประวัติพร้อมปุ่ม Export ใช้ Import backup กับไฟล์ที่ส่งออกเมื่อต้องการกู้คืน โดยไม่ทับโน้ตปัจจุบัน Export backup ปกติรวมประวัตินี้ด้วย และ import จะไม่เปลี่ยนประวัติให้เป็นสมุดอัตโนมัติ
- นำ migration เดิมที่ส่ง recovered pages กลับเข้า sync อัตโนมัติออก หน้าเก่าที่มีเนื้อหายังคงอยู่และใช้ Keep ได้
- เลิกโหลด payload ของประวัติทั้งหมดทุกครั้งที่ตรวจสถานะ sync

## สมุดว่างเก่าจากบั๊ก

หลัง pull ครบ จึงย้ายสมุดที่ชื่อจบด้วย ` · conflict` ไป Trash เมื่อมี revision จากเซิร์ฟเวอร์แล้ว ไม่มีหน้าใดเลย (นับหน้าที่อยู่ใน Trash ด้วย) และไม่มี notebook operation ค้างในเครื่อง

เก็บชื่อเดิมใน Saved versions และเอา suffix ที่ระบบสร้างออกจากชื่อใน Trash เพื่อให้ Restore บนอีกเครื่องไม่ทำให้ถูกจัดเก็บซ้ำ ไม่มีการลบถาวร ไม่แตะสมุดที่มีหน้า สมุดปกติ หรือสมุดที่ยังมีการแก้ไขค้างอยู่ กระบวนการนี้จะมีผลเมื่ออุปกรณ์รันเว็บเวอร์ชันใหม่และ sync สำเร็จ

## การตรวจ

- SQLite จริง: สอง store แก้สมุดและหน้า offline พร้อมกัน 3 รอบ แล้ว retry/poll ต่อ จำนวนสมุดและหน้าไม่เพิ่ม ข้อมูลหลักตรงกัน คิวหมด และเวอร์ชันของอีกเครื่องยังส่งออกได้
- SQLite จริง: สมุดว่างซ้ำ 20 เล่มย้ายไป Trash; สมุดที่มีหน้าลบแล้ว สมุดปกติ และสมุดที่มีงานค้างไม่ถูกแตะ Restore และเปิดบนอีกเครื่องไม่ถูกจัดเก็บซ้ำ
- บันทึกประวัติและ marker อยู่ใน transaction เดียวกัน ทดสอบ disk failure แล้ว rollback พร้อมคง operation ต้นฉบับ
- ทดสอบ export/import backup ให้ประวัติยังอยู่โดยไม่สร้าง live pages เพิ่มจากประวัติ
- Chromium: seed สมุดซ้ำ 20 เล่มและสมุดจริง 1 เล่มลง SQLite ของเบราว์เซอร์ เปิดแอปใหม่ ตรวจ library เหลือสมุดจริง ส่งออก Saved version และเปิดแอปอีกครั้ง
