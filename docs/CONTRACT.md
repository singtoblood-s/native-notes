# Shared data and sync contract (v1)

This is the wire and local data contract for the NotePad progressive web app.
The same app runs in a browser on Android and iPadOS; pointer events preserve
pressure and tilt when the browser exposes them, while the server stores an
editable stroke snapshot that can be rendered again on either device.

## IDs and time

All IDs are lowercase UUID strings generated by the client for new objects.
Times are ISO-8601 UTC strings (for example `2026-09-11T05:00:00Z`). A server
revision or sequence, never a device clock, decides sync ordering.

## Common JSON models

`Notebook`:

```json
{
  "id": "uuid",
  "title": "My notebook",
  "createdAt": "2026-09-11T05:00:00Z",
  "updatedAt": "2026-09-11T05:00:00Z",
  "revision": 0,
  "deletedAt": null
}
```

`NotePage` is one fixed-size editable page. `background` is `blank`, `ruled`,
or `grid`; dimensions are logical points.

```json
{
  "id": "uuid",
  "notebookId": "uuid",
  "title": "Page 1",
  "text": "typed Thai or English text",
  "background": "blank",
  "width": 1024.0,
  "height": 1366.0,
  "strokes": [
    {
      "id": "uuid",
      "color": 4278190335,
      "width": 2.5,
      "points": [
        {"x": 12.0, "y": 20.0, "pressure": 0.7, "time": 0, "tiltX": 0.0, "tiltY": 0.0}
      ]
    }
  ],
  "formatVersion": 1,
  "revision": 0,
  "updatedAt": "2026-09-11T05:00:00Z",
  "deletedAt": null
}
```

`color` is unsigned 32-bit ARGB (`0xAARRGGBB`) represented as a JSON number.
Each point's `time` is milliseconds relative to the first point in its stroke.
`pressure` is normalized to 0..1; clients use 0.5 when the source device has
no pressure. `tiltX` and `tiltY` are optional degrees and may be null. Predicted
points are not persisted. A tap is stored as one point; clients ignore an
empty in-progress stroke before enqueueing it. A point's x/y are in page
coordinates, never screen coordinates.

## Client storage

The web client stores guest and account workspaces in separate browser
databases (SQLite WASM with an IndexedDB snapshot fallback) and writes the
snapshot plus its outbox entry in one transaction. The JVM `shared` module
contains only the serializable wire models used by the server and tests;
browser storage and canvas rendering stay in the PWA.

Both guest and account stores remain usable offline. Switching accounts must
close the old store and open a separate one so an outbox entry can never cross
account boundaries.

`webApp/src/coordinator.ts` owns the automatic sync lifecycle around the store
and editor. The UI creates it with `getStore`, `getSession`, and an optional
`SyncClient`, then calls `start()` after the current store is open,
`notifyAuthChanged()` after login/logout or an endpoint/workspace switch,
`notifyLocalWrite()` after each durable local save, `request("manual")` for an
explicit toolbar action, and `stop()` before closing the store. A local save is
debounced for 750 ms; visible startup, foreground, and online recovery run
immediately; visible idle work is checked every 60 seconds. Network failures
use bounded exponential backoff, while offline and guest workspaces never make
a request. `subscribe`/`onStatus` expose `pending`, `conflicts`, last attempt,
last success, and a user-facing error without treating a scheduled timer as a
successful sync. `onBeforeSync` must flush the active editor and may return
`false`; `onAfterSync` may reload the selected page only when its edit
generation is unchanged. The coordinator rechecks the generation and exact
`<endpoint>:<user-id>` workspace key after every awaited local check, so an
account or endpoint switch cannot upload an old workspace.

Changing the server endpoint does not transfer an old account workspace into a
new server account automatically. The old browser database and outbox remain
available through the saved workspace list for an explicit export/recovery
action.

When a conflict copy refers to a notebook that is missing or tombstoned in the
local workspace, the client creates a new recovery notebook and queues its
upsert before showing the recovered page. The recovered page remains local
until it is edited, so its next queued edit has a server-side parent.

## Sync API

All `/v1` endpoints require `Authorization: Bearer <sessionToken>` except
register/login. Tokens are opaque and are never persisted in the repository.

Register/login request and response:

```json
{"identifier":"user@example.com","password":"at-least-12-chars"}
```

```json
{
  "user": {"id":"uuid","identifier":"user@example.com"},
  "sessionToken":"opaque-token",
  "expiresAt":"2026-10-11T05:00:00Z"
}
```

`POST /v1/auth/register` creates the account; `POST /v1/auth/login` returns a
new revocable session. `POST /v1/auth/logout` revokes the current session.

Push uses an immutable operation ID and compare-and-swap base revision:

`POST /v1/sync/push`

```json
{
  "operations": [
    {
      "opId":"uuid",
      "entityType":"page",
      "entityId":"uuid",
      "baseRevision":0,
      "action":"upsert",
      "payload": {"...": "complete Notebook or NotePage snapshot"}
    }
  ]
}
```

Response preserves input order:

```json
{
  "results": [
    {"opId":"uuid","status":"acked","revision":1,"sequence":42},
    {"opId":"uuid","status":"conflict","revision":2,"sequence":41,
     "serverPayload":{"...":"current snapshot"}}
  ],
  "cursor":42
}
```

An already-seen `opId` returns the original result and never creates a second
object. A conflict never overwrites the server snapshot. The client preserves
its rejected snapshot as a conflict copy with a new local ID and then pulls the
server snapshot. `delete` is a tombstone operation whose payload is the
complete current Notebook or NotePage snapshot; the server sets `deletedAt`
when it is absent and retains the tombstone for sync recovery. An ID-only
delete payload is invalid.

Pull uses a monotonic cursor and applies returned changes plus the new cursor
in one local transaction:

`GET /v1/sync/pull?cursor=0&limit=100`

```json
{
  "changes": [
    {"sequence":42,"entityType":"page","entityId":"uuid",
     "revision":1,"action":"upsert","payload":{"...":"snapshot"}}
  ],
  "nextCursor":42,
  "hasMore":false
}
```

Cursor `0` means initial sync. Limits are bounded by the server (maximum 100).
This v1 server does not prune its change log; it returns `409` with
`{"code":"cursor_expired"}` if a client cursor is ahead of the current sync
epoch. The client resets to cursor `0` and performs a full pull while retaining
unsent outbox operations.

## Error envelope

Errors use one shape and do not reveal whether an unknown login identifier
exists:

```json
{"error":{"code":"invalid_request","message":"safe user-facing text"}}
```

Clients retry only network/5xx failures and reuse the exact same request body
and `opId`. They do not retry 400/401/403/409 without handling the code.

## Deliberate v1 limits

Login is local identifier/password with PBKDF2-HMAC-SHA256 on the server; it
does not require Google provisioning. Transport must be TLS in deployment.
Push accepts at most 100 operations, 4 MiB per HTTP request, and 2 MiB per
operation payload. The PWA keeps its request batches below 3 MiB to leave room
for JSON framing and proxies.
The server can read note payloads; end-to-end encryption is a later contract.
Sync is snapshot plus revision CAS, with conflict copies; there is no realtime
collaboration or CRDT. Attachments and PDF backgrounds are outside v1.
